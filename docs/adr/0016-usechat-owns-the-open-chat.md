# useChat owns the open Chat's messages

The Chat screen uses `useChat` from `@ai-sdk/react`, and its message list is the single list the open Chat renders. That breaks the web rule against mirroring query results in React state ([apps/web/README.md](../../apps/web/README.md), "Server-state ownership"). We accept the exception for this one screen so that a turn keeps one element from the first streamed word to its saved form. Before, the streamed answer was thrown away and rebuilt from the cache. React Query still loads the Chat. Every refetch replaces the saved messages in `useChat` by ID and keeps a turn still being answered after them. That sync is what makes an answer withdrawn by a Source deletion disappear from an open Chat. After an answer is saved, the screen invalidates the Chat query and never writes the turn into the cache itself. The one cache write is when a Chat is created: the new, empty Chat is seeded so opening it needs no request.

Stable IDs make this work. The client creates the question's ID, which the stream route stores. It rejects an ID already used in any of the student's Chats with 409, and a concurrent request that reuses the ID with a `conflict` refusal when saving. The route also announces the answer's ID in the stream's `start` chunk before generating, so both messages already carry their saved IDs while they stream. A saved turn is only confirmed by `data-committed`, never by the end of the stream ([streaming-chat.md](../research/streaming-chat.md)). On Stop, a refusal or a broken stream, the turn is removed and the draft restored ahead of anything typed meanwhile. If a refetch then shows the turn was saved anyway, the draft is taken back out of the composer. The research behind this decision is in [chat-responsiveness.md](../research/chat-responsiveness.md).

**Amendment (2026-11-12, Chat tools, [ADR-0019](0019-the-chat-model-calls-tools.md)):** the stream is built from the AI SDK's `toUIMessageStream`, one per model step, merged into the route's stream. The route still writes the `start` chunk with the answer's ID and `data-committed` or `data-refused` itself. Tool calls are AI SDK tool parts whose output is only what the client shows. The request body stays strict: either a question (`{ id, text, model }`) or an approval (`{ approval: { id, fingerprint }, model }`). The server builds the history and the approved tool call from the database and never accepts messages from the client. A report after an Approval is a new assistant message with its own ID, so saved messages never change. The screen reads that report's stream itself and puts it into `useChat`'s list with `setMessages`. Sending through `useChat` would continue the answer the card belongs to and show its card twice. `POST /api/me/chats/{id}/messages`, which nothing called, is removed.

## Considered Options

- **React Query plus a hand-written stream reader (the previous design):** follows the rule, but the swap from the streamed answer to the saved one recreated its elements.
- **Split ownership:** Query keeps saved history and `useChat` holds only this visit's turns, matched by ID. It avoids the exception, but we preferred one list for the screen and the AI SDK's standard message model.
