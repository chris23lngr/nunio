## status: accepted

# Integration tool calls run where their Chat or Run runs

An Integration tool call reaches a service outside nunio, and a write may take effect even when no answer comes back ([Where Integration tool calls run, and what a write that never answers becomes](https://github.com/chris23lngr/nunio/issues/272)). We run each call where its Chat or Run already runs. Writes go through the gate like every other Action, so an Unconfirmed write is the gate's existing state, not a new mechanism.

- **Where.** A Chat turn's Integration reads and granted writes run in `apps/api`, inside the streaming request, like every other Chat tool ([ADR-0019](0019-the-chat-model-calls-tools.md)). An Agent's Run reads inside its step Activity and writes inside its Actions Activity in `apps/worker` ([ADR-0006](0006-one-workflow-per-run.md)). An approved write is performed by the API when the student decides, for a Chat and for a Run alike. The "Abgeben" button calls `email.submit` from the API without a model. Email's IMAP and SMTP layer runs in the same places, in process.
- **Clients and credentials.** A Chat or Run builds the tools it offers the model from the catalog's pinned definitions. A client (or an IMAP session) is opened on the first call of a turn or step and closed when it ends. For an MCP server, opening it lists the server's tools and compares them with the pins as [How the catalog classifies an MCP server's tools](https://github.com/chris23lngr/nunio/issues/262) decided: a tool that drifted is withheld for the rest of that turn or step, and staff are alerted. Each write opens its own client. Credentials are loaded from Postgres at the call, under the master key both the API and the worker hold ([ADR-0007](0007-hetzner-storage-with-nunio-managed-encryption.md)), and never enter Temporal payloads. A 401 that survives one refresh, an `invalid_grant`, or a rejected IMAP or SMTP login sets the Connection to Needs reconnection ([The lifecycle of a Connection](https://github.com/chris23lngr/nunio/issues/261)). Neither is retried, and the model is told the Connection is unavailable.
- **Writes are Actions.** Every Integration write goes through the gate with an Integration executor. It records an Attempt before the call and settles it after.
  - **Done:** the service answered with a result.
  - **Failed:** the service answered with an error (a tool error, a JSON-RPC error or a 4xx), or nothing was sent (DNS, TLS or a refused connection). Failed is never retried by nunio; the model is told why.
  - **Unconfirmed:** the request was sent and no answer came before the gate's 60-second timeout, the connection dropped after sending, or the service answered 5xx. For SMTP, Unconfirmed means the message data was sent and no `250` followed ([Whether Email makes an email Destination submittable](https://github.com/chris23lngr/nunio/issues/264)).
  - **No retries.** MCP and SMTP offer no idempotency, so the executor's lookup always answers "unknown". An Attempt that a dead API or worker left in flight becomes Unconfirmed when reconcile finds it, and is never sent again.
- **Reads are not Actions.** They take no effect, so they bypass the gate and may retry. Each read call has 30 seconds. After a transport failure, a 429 or a 5xx it is tried once more, honouring `Retry-After` up to 5 seconds, within the turn's or step's own deadline. A tool error or a 4xx is not retried. Every call counts toward the read limits ([ADR-0026](0026-an-agents-grants-accept-bounded-steering-by-its-material.md) amendment from [What bounds a Chat or Run that reads mail](https://github.com/chris23lngr/nunio/issues/265)), whether it fails or not.
- **Stopping never cuts a write.** A write the gate has dispatched runs to its own answer or timeout, whatever happens around it. The student pressing Stop, closing the tab, or Pausing or Ending the Agent does not abort it. Its outcome is recorded either way.
  - **Chat turns run to the end after a write.** Until a turn dispatches its first write, Stop and a closed tab end it and it records nothing, as before. From that write on, the turn ignores them, takes its remaining steps (at most 6 in all) and is saved, so the write shows in the Chat with its answer. ADR-0016's client already handles a stopped turn that a refetch shows was saved anyway. If such a turn still fails, through a model error or a refused step, it is saved with the parts it has, ending with nunio's fixed line that the answer was cut short.
  - **Runs stop after the write.** A Paused or Ended Agent's Run stops once the write in progress has its outcome. Today the workflow cancels the Actions Activity as soon as the stop signal arrives, so it must instead let a dispatched write settle before the Run finishes.
- **What the student sees of an Unconfirmed write.** Everything that already exists for an Unconfirmed Action. It raises one Intervention. In a Chat it is asked at the composer before anything else, and in a Run it stops the Run, which shows it in Activity as "Unbestätigt". The card shows the tool's nunio label, the Connection and every argument, with a fixed nunio line asking the student to check in that service. The student resolves it with the gate's existing resolution: it happened (done) or it did not (failed). Nothing is checked automatically in v1. A resolved write is not redone; doing it again is a new call with its own authority. For `email.submit` that is "Erneut abgeben" with a new Approval. Unconfirmed writes stay through Disconnect, but their sealed arguments are shredded with the Connection's key and the card shows the disconnected-content placeholder instead ([Where Integration content may flow](https://github.com/chris23lngr/nunio/issues/266)).
- **A Chat turn takes no further write after an Unconfirmed one.** Its later write calls in that turn are refused as `unconfirmed`, so the model cannot retry blindly. It may still read and answer. This matches a Run, which stops.
- **Counting.** A dispatched granted write counts toward the granted-write limits whatever its outcome, Failed and Unconfirmed included. Approved writes don't count toward them.
- **Activity timeouts.** A step's Actions Activity must outlast five writes at the gate's timeout, so its start-to-close timeout rises from 2 to 6 minutes.

The cost: a closed tab no longer always stops a Chat turn, and a crash of the API mid-turn after a write that took effect leaves that write only in the gate's record, with no answer in the Chat. We accept the second because it needs a crash at that moment, and the write had authority.

## Considered Options

- **Chat tool calls as Temporal Activities:** a durable turn, but a round trip per call. It would also split the model loop across the API and the worker, while the turn itself stays undurable (ADR-0016). The gate's Attempts and reconcile already make writes durable where it matters.
- **Aborting a dispatched write with the request:** frees the API sooner. But an aborted HTTP request may still take effect, so every Stop during a write would become Unconfirmed.
- **Saving the Chat turn before its writes run:** keeps "an interrupted turn records nothing". But the model could not use a write's result in the same turn, for example a new page's ID for the next call.
- **Retrying a timed-out write once:** fewer Unconfirmed writes, but a duplicate email or page when the first call did land.

## Amendment (2026-11-25): what a read costs and returns

A read costs nunio nothing at the service, so it gets no price of its own ([How Integration reads count against the Allowance and an Agent's Budget](https://github.com/chris23lngr/nunio/issues/273)).

- **Cost is model input.** A read's result costs only as input to the model steps that see it. Those steps are metered like every other ([ADR-0019](0019-the-chat-model-calls-tools.md)), against the Allowance and, in a Run, the Agent's Budget. A read runs inside a step that is already reserved, so it needs no reservation of its own. A Run's later steps resend what it read, so an early read is paid for again at each step.
- **At most 20,000 characters per result.** Every Integration result the model sees, from a read or a write, is cut at 20,000 characters, marked `truncated: true`, with no paging. This is `email.read`'s limit, now fixed. `email.search` keeps 20 hits by default and 50 at most, and past the cap drops whole hits from the end. Only text reaches the model: an MCP result's images, audio and binary resources each become one line naming their type and size. With the read limits, a Chat turn sees at most 200,000 characters of Integration read content and a Run 400,000.
- **No further bound on volume.** The read limits and the cap per result bound how much is read. The Budget and the Allowance bound what it costs, as for every step.
- **Running out mid-Run.** The Budget and the Allowance are checked when a step is reserved, not per Integration call. A step's Actions are performed before the next step is reserved. So a Run whose next step finds the Budget exhausted stops with `budget_exhausted` and its Agent is Paused, as today. Reads take no effect, so nothing is undone, and a write the model had not yet called is never made. A Chat turn refused at a step records nothing (ADR-0019), unless it already dispatched a write; then it is saved as above.
- **Shown as model cost.** A Run's cost, like the Agent's Budget and the student's Allowance, is shown as one model cost, with no separate Integration cost. Activity keeps no Integration cost, only structured labels, call counts and outcomes (see the next amendment, which refines the "item counts" of [Where Integration content may flow](https://github.com/chris23lngr/nunio/issues/266)).

Considered: a fixed price per read on the Budget, which would bound reads twice and invent a price for calls that cost nunio nothing; and a cap on a Run's total Integration characters, which the read limits times the cap per result already set.

## Amendment (2026-11-25): how Integration calls show in Activity

Activity keeps an Agent's Runs as long as the Agent, but Integration content may live only under its Connection's key ([Where Integration content may flow](https://github.com/chris23lngr/nunio/issues/266)). We decided how a Run's Integration calls show there ([How a Run's Integration calls appear in Activity](https://github.com/chris23lngr/nunio/issues/274)). Like every Verlauf entry, nunio renders them from structured events, never from what the model or the service wrote.

- **Reads are grouped.** A step's reads become one Verlauf entry per Connection, next to the step's other reads: the Integration's name, then each tool's catalog label with its number of calls, such as "E-Mail · Mails durchsuchen 3× · Mail lesen 1×". The event keeps the Integration, the Connection and, per tool, how many calls answered, failed or were refused (`run_cap` or `tool_unavailable`), and notes when the Connection was found to need reconnection. It counts calls, not items, refining the "item counts" of [Where Integration content may flow](https://github.com/chris23lngr/nunio/issues/266): a generic MCP result has no items nunio can count, and one `email.read` is one mail.
- **Writes are one entry each,** like a Plan Action: the tool's catalog label, the Connection and the gate's outcome. The event holds the Action's id, the Integration, the Connection, the tool and the outcome, never arguments. A write taken under a Connection's Grant reads "ohne Nachfrage (Immer erlaubt)".
- **Arguments come from the sealed Action.** Opening a write's entry shows every argument as the Approval card does, read from the Action and opened with the Connection's key when shown. Activity copies none of them, so ADR-0001's "with its arguments" holds while Activity itself holds no content, and deleting the Connection's key makes them unreadable in one place.
- **Why a granted write asked.** A write asked because the Run had read another Connection ([ADR-0026](0026-an-agents-grants-accept-bounded-steering-by-its-material.md), "Integration content") carries the card's fixed nunio line in its entry, naming that Connection's Integration; the event records that Connection and its Integration. A never-grantable write has no such line, since it always asks.
- **Outcomes in nunio's words only.** Done, asked, refused, failed and Unconfirmed show as for Plan Actions. A refusal names nunio's reason, such as `run_cap`, `open_approvals_cap`, `paused`, or `tool_unavailable` for a tool hidden or removed since it was offered. A failure names one of nunio's fixed reasons, kept in the Action's `failure`: the service reported an error, nothing was sent, or the Connection needs reconnection. The service's own error text is Integration content, so the model sees it fenced and Activity never keeps it. An Unconfirmed write stops the Run (`unconfirmed`), and its entry carries the line to check in that service.
- **Freigaben** shows a Run's open Integration Approvals with the card from [Integrations UI](https://github.com/chris23lngr/nunio/issues/267), beside its Plan Approvals. They count toward the Run's one Intervention ([ADR-0006](0006-one-workflow-per-run.md)) and expire like the others. A decided one becomes an Approval entry named by the tool's label. One that Disconnect withdrew reads "Verbindung getrennt, bevor du entschieden hast" (`disconnected`).
- **Zusammenfassung** works as today: a summary written after reading or writing through a Connection is sealed under its key as well, like one drawn from a Source. Once Disconnect has shredded it, it shows the disconnected-content placeholder below, not the line for a deleted Source.
- **After Disconnect** the entries stay, like all Activity. Labels, counts, outcomes and times are nunio's and the catalog's, so they still read, with the Integration marked "getrennt" because the Connection is deleted. Arguments, the summary and anything else sealed under the key show "Inhalt aus einer getrennten Verbindung". Connecting the Integration again makes a new Connection with a new key and restores nothing.

Considered: one entry per read, which floods the Verlauf at up to 20 reads per Run and says no more than a count; copying arguments into the event under the same key, which duplicates the Action; and keeping subjects or page titles in plain text for a more telling Verlauf, which [Where Integration content may flow](https://github.com/chris23lngr/nunio/issues/266) ruled out.
