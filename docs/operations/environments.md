## Founder invitations (Phase 3)

After building the workspace and applying its migrations, run from the repo root:

```sh
node --env-file=.env.invites packages/identity/dist/invite.js student@example.com
```

The ignored `.env.invites` file supplies `INVITATION_DATABASE_URL` (a pooled connection authorized to create invitations), `APP_ORIGIN` (the target app origin), and `OPERATOR_ID` (the operator's audit attribution). Database credentials authorize the command; `OPERATOR_ID` is operator-provided attribution, not a separate login.

The command prints one JSON record with the invitation ID, normalized email, operator, issuance time, expiry and shareable `/sign-in?invitation=…` URL. Share the URL manually with the intended student. It expires exactly seven days after issuance and is single-use. Only a SHA-256 hash of the random token is stored; the raw token appears only in the returned link. The database row retains the operator and issuance/acceptance timestamps.

This command creates an invitation, not an entitlement. Accepting it reserves it for a pending account; successful email verification activates that student's pilot entitlement. No invitation-issuing student endpoint exists.

## Pilot entitlements (Phase 3)

`GET /api/me/entitlement` requires a current, verified session and returns the current student's `status`: `active`, `revoked`, or `none`. Student IDs supplied in the URL or headers do not select another student's record. Signed-out and unverified sessions receive `401`. The response uses `Cache-Control: no-store` and reads current database state.

Pilot access has no expiry. An accepted invitation followed by email verification creates one entitlement; activation never clears an existing revocation. Verified legacy accounts without accepted invitations are not automatically enrolled and receive `none`.

If entitlement activation fails after the verified email flag has been saved, verified sign-in retries the activation before creating the new session. Once database access recovers, the student can sign in normally without a new invitation. Revoked entitlements remain revoked, with their original operator and timestamp.

After building the workspace and applying migrations, revoke an existing pilot entitlement from the repo root:

```sh
node --env-file=.env.operator packages/billing/dist/revoke-pilot.js STUDENT_ID
```

Supply `OPERATOR_DATABASE_URL` (a pooled operator connection) and `OPERATOR_ID` in the ignored `.env.operator` file. Use the student's ID from an authenticated session or operator database tooling. Database credentials authorize the command; the operator ID is audit attribution. The command prints the stored student ID, revocation timestamp and operator. Repeating it preserves the first revocation's audit record. A missing entitlement or operator causes a nonzero exit, without creating an entitlement.

Revocation changes entitlement status immediately but preserves sessions and read access. It does not suspend the account or delete data. Upload and AI entry points must enforce `active` status as those features arrive; Allowance amounts and atomic usage metering remain Phase 4.

Local API tests use Testcontainers Postgres and execute the real founder command. They cover activation, indefinite access, current-session checks, forged student IDs and audited revocation. This proves application-level selection of the student's record; separate runtime roles, forced RLS and pooled owner-context tests remain unfinished Phase 3 work. These changes are not yet verified on staging.

## Authentication email (Phase 3)

Scaleway TEM in `fr-par` is selected by [ADR-0013](../adr/0013-scaleway-for-authentication-email.md). Before deploying this slice, configure the API's `SCW_PROJECT_ID`, `SCW_SECRET_KEY` and `AUTH_EMAIL_FROM`; the app refuses to start when they are missing. Validate the sending domain and sender with Scaleway first. Keep the API key out of web/worker/parser environments.

Signup creates an unverified account without a session. Better Auth's verification links expire after one hour; following a valid link verifies the address, then the student signs in with their password. Invalid/expired links return to sign-in with recovery guidance. Pending students can resend verification without another invitation. Better Auth keeps signup successful even when delivery fails; the account remains pending, and resending can recover after provider access is restored. Provider errors do not expose response bodies, keys or verification links in our error messages.

Password recovery starts from the email field and **Forgot password?** button on sign-in; the current password is not required. Known and unknown addresses receive the same generic request response. The emailed link opens `/reset-password`, which is public so a signed-out student can recover access. Reset tokens expire after one hour and are consumed once. Completing a reset changes the password and revokes all existing sessions in the same database transaction; it does not sign the student in or verify a pending email address. Invalid/expired links return to recovery guidance, and the student requests a new link from sign-in.

Local auth/API integration tests use real Postgres and stub only outbound Scaleway HTTP. Browser session tests provision verified users through their operator connection and do not send emails to generated addresses. This is not a live delivery check.

Separate staging smoke test, still unperformed: issue an invitation for an owned mailbox, register through the app, confirm sign-in is refused before verification, receive and follow the message, then sign in successfully. Repeat resend and expired/invalid-link recovery. Request password recovery, follow the delivered link while signed out, set a new password, and confirm old sessions and the old password no longer work. Record DNS/sender validation and actual mailbox delivery before marking staging email verified; HTTP acceptance alone does not prove delivery. The provider DPA and metadata-deletion procedure remain part of the pre-pilot review under ADR-0013.

## Interim Vercel staging (2026-10-30)

Until the Pro team exists, staging runs as two Hobby projects in the personal scope. Hobby's terms are for non-commercial use, so this is for spikes only, and both projects move to the team before any pilot user sees them.

- Projects have Root Directory `apps/api` / `apps/web`; each `vercel.json` pins the framework, `fra1`, and a `buildCommand` that builds workspace dependencies through turbo first. Deploy from the **repo root**: `vercel pull --yes --environment=production`, `vercel build --prod`, `vercel deploy --prebuilt --prod`, with `VERCEL_ORG_ID` and `VERCEL_PROJECT_ID` set. Deploying from inside an app directory fails, because prebuilt output refers to dependencies by repo-root paths.
- Staging uses the projects' **production** environment (custom environments need Pro), with the staging domains attached.
- The API's Hono builder starts from compiled `dist/` (`outputDirectory`), and `src/index.ts` is the only candidate entry that imports `hono`. Building from TypeScript fails: the builder type-checks with its own module resolution, and that mixes the CommonJS and ESM types of `hono` and `@hono/zod-openapi`.
- Spike c code (the `/spike/raw-body` route and the `x-spike-pool` response headers) is mounted only while `SPIKE_ROUTES=true` is set on `nunio-api`, with `SPIKE_WEBHOOK_SECRET` as the HMAC key. The staging browser suite reads the same key from the untracked `apps/e2e/.env.staging` (`set -a; . ./.env.staging; set +a` before `E2E_TARGET=staging bunx playwright test`). Remove both variables, and the spike code, once billing brings the real Stripe webhook.
- Moving to the team: re-create both projects there, move the domains, copy the env vars (generate a new `BETTER_AUTH_SECRET`, which signs everyone out). In GitHub, delete the `staging` environment's `VERCEL_ORG_ID` override (or set it to the team), set the two project-id variables to the new projects, and make sure `VERCEL_TOKEN` can deploy to the team.

## CI (`.github/workflows/ci.yml`)

- **Every PR and push to `main`:** frozen install, `bun run build typecheck lint test` (Testcontainers on the runner's Docker), an `openapi.json` drift check, and the local Playwright suite (`*.nunio.test` names in the runner's `/etc/hosts`).
- **On `main` only, in order, each job only if the previous one passed:** `prisma migrate deploy` on the staging branch (unpooled URL), deploy `nunio-api`, deploy the Render parser and then the worker (`.github/scripts/render-deploy.sh`, pinned to the commit), deploy `nunio-web`, then the staging browser suite. The `spikes` job (spike e against the staging buckets, spike f against OpenRouter) runs alongside this chain. A failing migration stops the pipeline before any deploy. Runs on `main` never overlap.
- Deploys use `vercel@65.8.0` with `pull` / `build --prod` / `deploy --prebuilt --prod` from the repo root (`.github/actions/vercel-deploy`).
- Not in CI yet: production. Both Render services track `phase-2/scaffold` until PR #1 merges; then switch their branch to `main`. Vercel's Git integration stays off for `main` (`git.deploymentEnabled.main: false`).
