## Interim Vercel staging (2026-10-30)

Until the Pro team exists, staging runs as two Hobby projects in the personal scope. Hobby's terms are for non-commercial use, so this is for spikes only, and both projects move to the team before any pilot user sees them.

- Projects have Root Directory `apps/api` / `apps/web`; each `vercel.json` pins the framework, `fra1`, and a `buildCommand` that builds workspace dependencies through turbo first. Deploy from the **repo root**: `vercel pull --yes --environment=production`, `vercel build --prod`, `vercel deploy --prebuilt --prod`, with `VERCEL_ORG_ID` and `VERCEL_PROJECT_ID` set. Deploying from inside an app directory fails, because prebuilt output refers to dependencies by repo-root paths.
- Staging uses the projects' **production** environment (custom environments need Pro), with the staging domains attached.
- The API's Hono builder starts from compiled `dist/` (`outputDirectory`), and `src/index.ts` is the only candidate entry that imports `hono`. Building from TypeScript fails: the builder type-checks with its own module resolution, and that mixes the CommonJS and ESM types of `hono` and `@hono/zod-openapi`.
- Spike c code (the `/spike/raw-body` route and the `x-spike-pool` response headers) is mounted only while `SPIKE_ROUTES=true` is set on `nunio-api`, with `SPIKE_WEBHOOK_SECRET` as the HMAC key. The staging browser suite reads the same key from the untracked `apps/e2e/.env.staging` (`set -a; . ./.env.staging; set +a` before `E2E_TARGET=staging bunx playwright test`). Remove both variables, and the spike code, once billing brings the real Stripe webhook.
- Moving to the team: re-create both projects there, move the domains, copy the env vars (generate a new `BETTER_AUTH_SECRET`, which signs everyone out). In GitHub, delete the `staging` environment's `VERCEL_ORG_ID` override (or set it to the team), set the two project-id variables to the new projects, and make sure `VERCEL_TOKEN` can deploy to the team.

## Hetzner buckets (staging)

`nunio-staging-quarantine` (7-day expiry, CORS PUT) and `nunio-staging-sources` (versioned, noncurrent versions expire after 30 days, CORS GET) in `fsn1`. Both are configured by `packages/knowledge/spike-e/provision.ts`, which is safe to re-run. CORS allows the SSE-C headers from `HETZNER_CORS_ORIGINS` (staging: `https://app.staging.nunio.app,https://app.nunio.test:8443`). Production buckets come with the Pro-team move.

## CI (`.github/workflows/ci.yml`)

- **Every PR and push to `main`:** frozen install, `bun run build typecheck lint test` (Testcontainers on the runner's Docker), an `openapi.json` drift check, and the local Playwright suite (`*.nunio.test` names in the runner's `/etc/hosts`).
- **On `main` only, in order, each job only if the previous one passed:** `prisma migrate deploy` on the staging branch (unpooled URL), deploy `nunio-api`, deploy the Render worker (`.github/scripts/render-deploy.sh`, pinned to the commit), deploy `nunio-web`, then the staging browser suite. The `spikes` job (spike e against the staging buckets, spike f against OpenRouter) runs alongside this chain. A failing migration stops the pipeline before any deploy. Runs on `main` never overlap.
- Deploys use `vercel@65.8.0` with `pull` / `build --prod` / `deploy --prebuilt --prod` from the repo root (`.github/actions/vercel-deploy`).
- Not in CI yet: the `parser` service (spike g) and production. The Render worker service tracks `phase-2/scaffold` until PR #1 merges; then switch its branch to `main`. Vercel's Git integration stays off for `main` (`git.deploymentEnabled.main: false`).
