## Founder invitations (Phase 3)

After building the workspace and applying its migrations, run from the repo root:

```sh
node --env-file=.env.invites packages/identity/dist/invite.js student@example.com
```

The ignored `.env.invites` file supplies `INVITATION_DATABASE_URL` (a pooled connection authorized to create invitations), `APP_ORIGIN` (the target app origin), and `OPERATOR_ID` (the operator's audit attribution). Database credentials authorize the command; `OPERATOR_ID` is operator-provided attribution, not a separate login.

The command prints one JSON record with the invitation ID, normalized email, operator, issuance time, expiry and shareable `/sign-in?invitation=…` URL. Share the URL manually with the intended student. It expires exactly seven days after issuance and is single-use. Only a SHA-256 hash of the random token is stored; the raw token appears only in the returned link. The database row retains the operator and issuance/acceptance timestamps.

This command creates an invitation, not an entitlement. Accepting it reserves it for a pending account; successful email verification activates that student's pilot entitlement. No invitation-issuing student endpoint exists.

## Pilot entitlements (Phase 3)

`GET /api/me/entitlement` requires a current, verified session and returns the current student's `status`: `active`, `revoked`, or `none`. Student IDs supplied in the URL or headers do not select another student's record. Signed-out and unverified sessions receive `401`. The response uses `Cache-Control: no-store` and reads current database state.

Pilot access has no expiry. An accepted invitation followed by email verification creates one entitlement; activation never clears an existing revocation. Verified legacy accounts without accepted invitations are not automatically enrolled and receive `none`.

If entitlement activation fails after the verified email flag has been saved, verified sign-in retries the activation before creating the new session. Once database access recovers, the student can sign in normally without a new invitation. Revoked entitlements remain revoked, with their original operator and timestamp.

After building the workspace and applying migrations, revoke an existing pilot entitlement from the repo root:

```sh
node --env-file=.env.operator packages/billing/dist/revoke-pilot.js STUDENT_ID
```

Supply `OPERATOR_DATABASE_URL` (a pooled operator connection; see "Database roles" for its minimum privileges) and `OPERATOR_ID` in the ignored `.env.operator` file. Use the student's ID from an authenticated session or operator database tooling. Database credentials authorize the command; the operator ID is audit attribution. The command prints the stored student ID, revocation timestamp and operator. Repeating it preserves the first revocation's audit record. A missing entitlement or operator causes a nonzero exit, without creating an entitlement.

Revocation changes entitlement status immediately but preserves sessions and read access. It does not suspend the account or delete data. Metered AI calls refuse revoked students (see "Allowance and metering"); upload entry points must enforce `active` status when they arrive in Phase 5.

Local API tests use Testcontainers Postgres, run the API as a `nunio_runtime` login and execute the real founder command. They cover activation, indefinite access, current-session checks, forged student IDs and audited revocation. `packages/delegation` tests forced RLS and pooled owner context under the same role. On staging (2026-10-30), activation, current-session checks and the origin guard were exercised through the app; founder revocation has not yet been run there.

## Allowance and metering (Phase 4)

Each student's Allowance counts AI usage in micro-USD of model cost (1,000,000 = $1). Activation grants $5; nothing resets it, and only the founder raises it. `GET /api/me/allowance` returns the current student's `limitMicroUsd`, `usedMicroUsd` and `heldMicroUsd`. Students without pilot access read an empty Allowance.

Every model call goes through `meter` in `packages/delegation`, which works in three steps:

1. It reserves the estimate in one conditional update and records a `usage_reservation` row, so concurrent calls never overspend. It refuses `allowance_exhausted`, `not_entitled` (no or revoked pilot access) and `ai_disabled` as values.
2. It runs the call.
3. It settles the actual cost. A provider's 4xx rejection (other than 408) releases the reservation. Timeouts, network errors and 5xx responses mark it `held`, because the call may have been charged; held usage still counts against the Allowance until the founder settles it.

Costs come from `packages/ai`'s registry:

- **Estimates** are a guaranteed upper bound for text input. Each text the request sends counts as its UTF-8 byte length plus 200 tokens of framing; a token never covers less than one byte. The full 8,000-token output budget is added, at OpenRouter's prices recorded in the registry.
- **Actual costs** are OpenRouter's reported cost per call (usage accounting is on for every request). If no cost is reported, the token counts are priced instead.

Only the allowlisted Haiku, Sonnet and Opus 5.5 IDs resolve. Every request is restricted to zero-retention endpoints and SDK retries are off. The `main` pipeline's spike f job checks the cost field and the estimate bound against the live API.

Raise a student's Allowance from the repo root after building:

```sh
node --env-file=.env.operator packages/billing/dist/grant-allowance.js STUDENT_ID 2.50
```

The amount is in USD, up to six decimals. The command prints the student ID, the amount granted, the new limit, the operator and the time, and appends an `allowance_grant` audit row. Each run adds again. It fails without changes for a malformed amount or a student without an Allowance. On top of the revocation privileges, the operator connection needs `SELECT, UPDATE ("limitMicroUsd", "updatedAt")` on `allowance` and `SELECT, INSERT` on `allowance_grant`. The runtime role can move usage but cannot change a limit or read grants.

To settle held calls, list them over an owner connection:

```sql
SELECT "id", "studentId", "estimateMicroUsd", "reservedAt" FROM usage_reservation WHERE "status" = 'held';
```

Look up each call's cost in OpenRouter's activity log around `reservedAt`, then settle it with that cost, or `0` if it was not charged:

```sh
node --env-file=.env.operator packages/delegation/dist/settle-held.js STUDENT_ID RESERVATION_ID 0.00012
```

The command charges the actual cost, frees the rest of the estimate, and records the operator. It refuses anything that is not a held reservation of that student, so repeating it never charges twice. The operator connection needs these privileges:

- `SELECT, UPDATE ("status", "actualMicroUsd", "settledAt", "settledBy")` on `usage_reservation`;
- `SELECT, UPDATE ("usedMicroUsd", "heldMicroUsd", "updatedAt")` on `allowance`;
- `SELECT, UPDATE ("usedMicroUsd", "heldMicroUsd")` on `responsibility`, for calls made in a Responsibility's Run.

Set `AI_DISABLED=true` on `nunio-api` and the Render worker and redeploy both to stop all new model calls; Allowance reads keep working. Verified with Testcontainers under the runtime role. On 2026-11-02 the founder confirmed all manual Phase 4 staging checks passed (Allowance read, founder grant/audit, and kill switch).

## Sessions and deletion requests (Phase 3)

Students list and revoke sessions, or sign out everywhere, from `/account`. `POST /api/me/deletion-request` requires the student's password, records the request and ends every session in one transaction; later sign-in is refused. Mutations under `/api/me/*` are accepted only from `APP_ORIGIN`.

Completion is manual and not yet scripted. List pending requests over an owner connection with `SELECT "studentId", "requestedAt" FROM deletion_request;`. Deleting the `user` row as the owner currently cascades to its sessions, accounts, entitlement, Allowance (with its grants) and request.

## Database roles (Phase 3)

Migrations run as the table owner (`DATABASE_URL_UNPOOLED`) and create the `nunio_runtime` group role, which cannot log in. The API connects as a per-environment login in that group, never as the owner or a `BYPASSRLS` role. Student-owned tables use forced RLS keyed on the transaction-local `app.owner_id` that `withOwner` sets; auth tables are limited by grants, column-scoped for `user` and `invitation` updates, and the runtime role cannot issue invitations or update revocations.

Vercel applies environment changes only to new deployments, so provision the login before merging the migration:

1. On the target branch, as the owner, run `CREATE ROLE nunio_runtime NOLOGIN;` then `CREATE ROLE nunio_api LOGIN PASSWORD '…' IN ROLE nunio_runtime;` with a generated password (Neon requires at least 60 bits of entropy). The migration skips existing roles.
2. Confirm the pooled URL for `nunio_api` connects, store it in Vaultwarden, and set it as Vercel `nunio-api`'s `DATABASE_URL` without redeploying.
3. Merge. CI's migrate job grants privileges, then the API deployment picks up the new URL. A redeploy between steps 2 and 3 would run without grants.

Staging (2026-10-30): `nunio_api` is provisioned in `nunio_runtime` without `BYPASSRLS` and the API connects through the pooler with it; production has no runtime login yet.

Operator commands keep separate connections. `revoke-pilot` sets `app.owner_id` to the target student inside its transaction, so it needs neither superuser nor `BYPASSRLS`: `USAGE` on the schema and `SELECT, UPDATE` on `pilot_entitlement` suffice.

## Authentication email (Phase 3)

Scaleway TEM in `fr-par` is selected by [ADR-0013](../adr/0013-scaleway-for-authentication-email.md). Before deploying this slice, configure the API's `SCW_PROJECT_ID`, `SCW_SECRET_KEY` and `AUTH_EMAIL_FROM`; the app refuses to start when they are missing. Validate the sending domain and sender with Scaleway first. The key's IAM application needs a policy granting `TransactionalEmailEmailApiCreate` on the project (the SMTP permission set does not cover the HTTP API); without it every send fails and Scaleway records no email. Keep the API key out of web/worker/parser environments; the worker sends notification email with its own key (see "Notification email").

Signup creates an unverified account without a session. Better Auth's verification links expire after one hour; following a valid link verifies the address, then the student signs in with their password. Invalid/expired links return to sign-in with recovery guidance. Pending students can resend verification without another invitation. Better Auth keeps signup successful even when delivery fails; the account remains pending, and resending can recover after provider access is restored. Provider errors do not expose response bodies, keys or verification links in our error messages.

Password recovery starts from the email field and **Forgot password?** button on sign-in; the current password is not required. Known and unknown addresses receive the same generic request response. The emailed link opens `/reset-password`, which is public so a signed-out student can recover access. Reset tokens expire after one hour and are consumed once. Completing a reset changes the password and revokes all existing sessions in the same database transaction; it does not sign the student in or verify a pending email address. Invalid/expired links return to recovery guidance, and the student requests a new link from sign-in.

Local auth/API integration tests use real Postgres and stub only outbound Scaleway HTTP. Browser session tests provision verified users through their operator connection and do not send emails to generated addresses. This is not a live delivery check.

Request password recovery, follow the delivered link while signed out, set a new password, and confirm old sessions and the old password no longer work. Then, from `/account`, revoke a session, sign out everywhere, and request deletion of a throwaway account. Repeat this test against production before its first student; HTTP acceptance alone does not prove delivery. ## PDF Sources (Phase 5)

The pilot accepts PDF only, including scans: at most 20 MiB and 100 pages per Source. The parser also caps decompressed streams at 32 MiB, extracted text at 2 MiB, each rendered PNG at 2 MiB/1568 pixels per side, and its response at 16 MiB. The worker bounds the parser response, chunk input and embedding batches. These are pilot implementation limits, not configurable student settings.

### Configuration before deployment

Provision in the platform secret stores, never in chat or committed files:

- **Vercel API and Render worker:** `SOURCE_KEY_VERSION=v1` and `SOURCE_MASTER_KEYS`, a JSON object mapping version IDs to base64-encoded 32-byte storage-wrapping master keys, for example `{"v1":"<base64 storage-wrapping key>"}`. Use the existing environment-specific `storage-wrap-*-v1` secret. Retain old versions during rotation. This key is separate from the Temporal `CODEC_KEY`.
- **Vercel API and Render worker:** existing `HETZNER_S3_ENDPOINT`, `HETZNER_S3_REGION`, `HETZNER_QUARANTINE_BUCKET`, `HETZNER_SOURCES_BUCKET`, `HETZNER_S3_ACCESS_KEY_ID`, `HETZNER_S3_SECRET_ACCESS_KEY`. Credentials need read/write/delete, multipart copy, and source-version listing/deletion. Buckets and CORS remain as verified in spike e.
- **Vercel API:** the worker's `TEMPORAL_ADDRESS`, `TEMPORAL_NAMESPACE`, `TEMPORAL_TASK_QUEUE`, `TEMPORAL_API_KEY`, `CODEC_KEY_VERSION` and `CODEC_KEY`. Both clients use the same payload codec and queue. During a codec key rotation, set optional `CODEC_PREVIOUS_KEYS` on the API and worker, a JSON object mapping retired version IDs to base64-encoded 32-byte keys, for example `{"v1":"<base64 codec key>"}`; those keys only decode existing histories, and `CODEC_KEY` encodes. The API starts deterministic `ingestSource/<Source ID>` and `deleteSource/<Source ID>` workflow IDs.
- **Render worker:** a pooled `DATABASE_URL` for a login in `nunio_runtime`, plus `OPENROUTER_API_KEY` and `OPENROUTER_BASE_URL`. The global kill switch must be set on the worker as well as the API now that ingestion invokes models. Model calls remain ZDR-only; international routing is the existing temporary ADR-0012 exception, not EU verification.
- **Parser only:** non-secret `PARSER_STORAGE_ENDPOINT` and `PARSER_QUARANTINE_BUCKET` matching storage. No database, provider, storage credentials, master keys or codec keys. The entrypoint rejects secret-like environment names, including `SOURCE_MASTER_KEYS`. Render passes the worker its private parser host through `PARSER_HOSTPORT`.

Apply the new Source migration before deploying the API and worker. Set the Render worker and parser values above **before** their first deploy: Blueprint `sync: false` values start empty. The worker and parser refuse to start without their settings (the worker names every missing one), so a missing value fails the deploy rather than each ingestion. Render keeps the previous worker instance polling for about three minutes after a new one is live, so after changing worker settings, the old instance can still take work under its old settings for that long. Real student data remains prohibited until the pilot-readiness gates pass.

### Upload and ingestion

The signed-in browser requests `POST /api/me/sources`, PUTs the PDF directly to the returned URL with its SSE-C headers, then POSTs `/api/me/sources/<id>/complete`. The signed Content-Length prevents a larger body. Only the owner's browser receives the file key; it never receives a master key. Listings omit all key material.

**Upload replacement race:** Hetzner's multipart copy did not enforce `CopySourceIfMatch` in the live check on 2026-11-02. The worker therefore first copies the upload to a worker-only `sealed/<id>` key _inside quarantine_. It parses that fixed copy and promotes only that copy. Replaying the browser PUT cannot change the parsed or promoted content. The regression is `packages/knowledge/spike-e/source-snapshot.test.ts`.

The Sources list polls every 5 seconds while it is open. There is no push channel yet, and at pilot scale polling is the simplest way to show `queued` → `ready`/`failed`.

The parser runs qpdf and Poppler in the separate secretless container, with subprocess CPU/address-space/file-size limits on Linux, per-command deadlines and an overall parse deadline. It fetches only HTTPS URLs under the configured quarantine bucket, refuses redirects, checks the actual size and signature, rejects malformed/decompression-heavy PDFs, and renders pages with little extractable text for Claude transcription; that transcription is added to any extracted text, never substituted for it. Application URL restrictions are not an OS-level egress firewall. The parser handles one request at a time and answers `503 busy` to any other, because its memory and CPU limits are sized for a single PDF. The worker waits out that refusal with backoff (up to the ingestion Activity's timeout), so concurrent ingestions queue for the parser instead of failing; other parser refusals still fail the Source.

All scan transcription and embedding requests go through `meter`. The initial embedding model is `baai/bge-m3`, 1024 dimensions, selected after a synthetic German/English comparison with Titan V2; both tied on this small fixture and BGE's listed input price was lower. Catalog expiration and ZDR availability were checked immediately before the eval. Results: [embedding eval](phase-5-embedding-eval.json), [German scan eval](phase-5-scan-eval.json). These fixtures are smoke checks, not pilot-quality thresholds. Chunk ciphertext, Source ownership, model ID, dimensions and pgvector values are stored together; publication is atomic and rechecks liveness and pilot access.

### Failures and recovery

Ingestion uses one 15-minute Activity with heartbeats and **one attempt**. A whole-Activity retry could repeat a model call already charged. Known errors mark the Source `failed`, including a Source key the worker cannot unwrap (its `SOURCE_MASTER_KEYS` differ from the API's); a worker crash can leave it `processing`. Until Phase 9 reconciliation, the founder investigates Temporal history/provider activity and reserved or held usage before any manual retry. Do not blindly reset a Source to `queued` or repeat paid work. The student sees processing stopped; no partial chunks are published. Automatic recovery and a founder retry command are not implemented in Phase 5.

Workflow arguments/results contain only student/Source IDs, timing and status, never unwrapped keys, page text, images or chunk text. Payload encryption alone would not make such content deletable with its Source key.

### Source deletion

`DELETE /api/me/sources/<id>` remains available to revoked students with a valid session. It verifies ownership and starts durable cleanup before changing the Source, so a dispatch failure leaves the request retryable. The API and worker can each finish the deletion idempotently. In one locked transaction deletion removes all chunks/vectors, shreds the wrapped key, clears the title and marks the Source deleted. Listings immediately exclude it, and ingestion rechecks the tombstone before publishing. Phase 7 retrieval must apply the same liveness rule; retrieval is not implemented yet.

A durable deletion workflow removes quarantine originals/snapshots and **every** stored source version and delete marker, then sweeps again after 20 minutes. This catches a still-valid upload URL and a bounded in-flight ingestion. Versions are deleted explicitly rather than left to the bucket's 30-day noncurrent expiry. The shredded key already makes them unreadable, but explicit deletion means a deleted Source's ciphertext does not depend on a lifecycle rule. Repeating deletion retries workflow dispatch safely. Key shredding hides Source content from nunio immediately; physical object deletion is asynchronous, and a browser that previously received the file key can retain its own copy. Existing presigned URLs may remain usable until cleanup/expiry. Database backup recovery of wrapped keys is bounded by the existing 30-day restore window. Do not claim synchronous physical deletion with every previously distributed key. During manual account deletion, keep the User and Source tombstones until their cleanup workflows finish; deleting them first would remove the ownership records needed by cleanup.
