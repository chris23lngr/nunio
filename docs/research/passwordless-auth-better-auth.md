# Passwordless sign-in with Better Auth: email OTP and passkeys

Research date: 2026-11-21. Inputs: [identity and pilot access](../design/identity-and-pilot-access.md), [ADR-0005](../adr/0005-separate-app-and-api-origins.md), [ADR-0013](../adr/0013-scaleway-for-authentication-email.md), [identity research](identity-billing-security.md), `packages/identity/src/*`, `packages/db/prisma/identity.prisma`, and the web and e2e auth code. External facts come from the Better Auth 1.7.14 package source (the version pinned in `packages/identity`, `apps/api`, `apps/web`, `apps/e2e`), the `@better-auth/passkey` 1.7.14 and 1.7.16–1.7.27 tarballs from the npm registry, Better Auth's docs (`better-auth.com/llms.txt/docs/...`, which track the latest release), GitHub release notes and open issues, the W3C WebAuthn Level 3 Recommendation, and SimpleWebAuthn's package and docs. This worktree has no `node_modules`, so the installed 1.7.14 source was read from Bun's install cache (`~/.bun/install/cache/better-auth@1.7.14`, `@better-auth/core@1.7.14`). No code was changed, nothing was installed into the repo, and no service was called except to read docs and source. The task mentions `packages/identity/src/rate-limit.ts`, but that file does not exist. The limiter helper is `admitPasswordAttempt` in `auth.ts`, and `rate-limit.test.ts` tests Better Auth's own limiter. Anything marked **proposal** is a recommendation, not a decision.

## Finding and recommendation

**Verified, in short:**

- **Email OTP is built into `better-auth` 1.7.14 (`better-auth/plugins`, `emailOTP`). Passkeys are not.** Passkeys are the separate package `@better-auth/passkey`, which declares `better-auth ^1.7.14` as a peer dependency and depends on `@simplewebauthn/server ^13.3.2` and `@simplewebauthn/browser ^13.3.0` (P1). The 1.7.14 `better-auth` package exports no passkey entry point (P1).
- **Pin `@better-auth/passkey` at 1.7.16 or later, and move `better-auth` to the same version.** In 1.7.14, `userVerification: "required"` is not enforced: both verify calls pass `requireUserVerification: false`, and authentication hardcodes `"preferred"` (P2, P3). Without an `origin` option, the expected WebAuthn origin is taken from the request's `Origin` header (P2, P3). 1.7.16 fixed both. It also made registration check the authoritative session store (P7, G1). The latest release is 1.7.27, from 2026-11-20 (P1).
- **OTP sign-in creates the account, and the repo's invitation hook still applies.** `/sign-in/email-otp` creates a missing user with `emailVerified: true`, unless `disableSignUp` is set (E4). It goes through `internalAdapter.createUser`, so `databaseHooks.user.create.before` runs with the request context and headers (C7). The existing `x-invitation-token` claim therefore still gates account creation. Two things change, though. Unlike `/sign-up/email`, the OTP route does not wrap the claim and the insert in one transaction (E4, C7). And by default, the plugin emails a code to any address that has no account (E3), so `/email-otp/send-verification-otp` needs an invitation check too (proposal below).
- **OTP sign-in marks the email verified but never calls `afterEmailVerification`** (E4). The repo's `session.create.before` hook activates the pilot whenever a verified user without an entitlement gets a session (R1). That hook becomes the main activation path rather than the retry path. No new activation code is needed.
- **Brute-force protection is per code and per IP, never per email address.** By default a code has 6 digits from `crypto.getRandomValues`, expires after 300 s, and allows 3 attempts. Attempt counting is atomic on `/sign-in/email-otp` (E1, E5). The plugin limits each of its routes to 3 requests per 60 s per IP, and those limits go through the repo's Postgres limiter (E2, C5). Nothing limits codes per email address (G3, open). From one IP, an attacker can make about 3 guesses a minute against one address, about 4,300 a day. That is roughly a 0.4 % daily chance of hitting a 6-digit code, and it grows linearly with the number of IPs. nunio needs its own per-email limit (proposal).
- **Turning off `emailAndPassword` only closes `/sign-in/email` and `/sign-up/email`** (C1). Other password routes stay mounted. `/verify-password` and `/change-password` would act on any remaining `credential` row (C4). The emailOTP plugin's own `/email-otp/reset-password` creates a `credential` account when one is missing (E7). Removing passwords therefore also means listing those routes in `disabledPaths`, which answers them with 404 (C2), and deleting the `credential` rows.
- **Better Auth has no step-up re-authentication without a password.** Its "fresh session" rule only compares the session's `createdAt` with `freshAge`, which defaults to 1 day. Refreshing a session updates `expiresAt` but not `createdAt` (C3, C9). A request to re-authenticate the current session without creating a new one is open (G4). Re-authentication means signing in again with an OTP or a passkey, which creates a new session. nunio then checks that the session is less than ten minutes old.
- **Passkeys can be added only from a signed-in session by default.** `registration.requireSession` defaults to `true` and also requires a fresh session (P2). Registering a passkey before an account exists works with `requireSession: false` plus `resolveUser` and `afterVerification`. In that case nunio creates the user itself, and nothing proves the email address (P2, P8). Since pilot access depends on a verified email, passkey-first sign-up adds nothing over signing up with an OTP and then adding a passkey.
- **With separate app and API origins, `rpID` and `origin` must be set explicitly.** The default `rpID` is the hostname of `baseURL`, which is `api.nunio.app` (P2). WebAuthn only allows an RP ID equal to, or a registrable domain suffix of, the calling origin's domain (W1). `app.nunio.app` cannot use `api.nunio.app`, so ceremonies started from the app would fail. The ceremonies run in the browser on `app.`, and their results are verified on `api.`. The challenge cookie is set by the API response, as the session cookie is (P2, R3).

**Proposed direction (details in "Fit with nunio's constraints"):** sign-up and sign-in by email OTP, with the invitation enforced on code send and on account creation. After sign-in, offer to add a passkey. Passkey sign-in supports autofill. Recovery is always by email OTP. Upgrade to Better Auth and passkey ≥ 1.7.16 with `userVerification: "required"`, an explicit `rpID` and an explicit `origin`. Add per-email limits on code sends and guesses. Disable every password route and delete the `credential` rows. Replace password confirmation for sensitive actions with "signed in within the last ten minutes."

## Email OTP plugin (1.7.14)

**Configuration and storage (E1, E6).** OTP length, expiry, attempts, how codes are stored, and whether a resend rotates or reuses the code are all configurable. Codes are stored in the existing `verification` table under the identifier `"<type>-otp-<email>"`, with the value `"<stored>:<attempts>"`. No new tables are needed. `storeOTP` defaults to plain text. `"hashed"` is a plain SHA-256 of a 6-digit code, so someone who can read the database recovers it in about 10⁶ hashes. `"encrypted"` (keyed by the auth secret) actually protects codes at rest. The 300 s expiry limits exposure in every mode.

**Send (E3).** `POST /email-otp/send-verification-otp {email, type}` (client: `authClient.emailOtp.sendVerificationOtp`). For an address with no account, a code is sent only for `type: "sign-in"`, and only while `disableSignUp` is false. In every other case the response is the same `{success: true}` and no email goes out. The send function is awaited, but its errors are swallowed (C8, G8). A Scaleway failure therefore looks like success to the student. The same is already true of today's verification-link emails.

**Sign-in (E4).** `POST /sign-in/email-otp {email, otp, name?, image?, ...additionalFields}` (client: `authClient.signIn.emailOtp`). There are three cases:

- **Unknown address, sign-up allowed:** the user is created with `emailVerified: true` and gets a session.
- **Existing unverified user:** every `account` row and session of that user is deleted first, then the user is marked verified (C6). This removes any password an unverified account had.
- **Existing verified user:** a session is created.

`createSession` is always called without "don't remember me", so OTP sessions get the full 30-day `expiresIn` that the repo configures (R1). The current "remember me" checkbox has no equivalent here.

**Brute force (E2, E5, C5, G3, G7, G10).** Each code allows 3 wrong attempts, and the sign-in check is atomic. Each OTP route allows 3 requests per 60 s per IP. Nothing limits sends or guesses per email address. Rotating IPs bypasses the per-IP limit, and each new code resets the 3-guess budget. Wrong-code responses differ between existing and unknown addresses (G7), which reveals whether an address has an account.

**Other endpoints worth knowing.**

- `/email-otp/verify-email` calls `before/afterEmailVerification`, unlike sign-in.
- `/email-otp/check-verification-otp` checks a code without consuming it. It is not atomic in 1.7.14 (E5).
- `createVerificationOTP` and `getVerificationOTP` are server-only.
- `change-email` with OTP is off by default.
- `/email-otp/request-password-reset`, `/email-otp/reset-password` and the deprecated `/forget-password/email-otp` exist only for password reset. Disable them (E7).

## Passkey plugin (`@better-auth/passkey`)

**Package and versions (P1, P7, G1).** It is a separate package and must be installed at the same version as `better-auth` (peer `^1.7.14`). It uses SimpleWebAuthn 13. The 1.7.14 build has two problems for a passwordless setup:

1. User verification cannot be required. It is `"preferred"` everywhere, and verification passes `requireUserVerification: false` (P2, P3). A passkey response without UV proves possession of the device, not that the person unlocked it. The WebAuthn spec leaves it to the RP to require the UV flag (W2).
2. The expected origin comes from the request header when `origin` is not set (P2).

In 1.7.14, nunio can work around the first problem by rejecting `!verification.authenticationInfo.userVerified` in `authentication.afterVerification` and `!verification.registrationInfo.userVerified` in `registration.afterVerification`. These SimpleWebAuthn v13 fields are verified (W3). The second problem goes away by always setting `origin`. Upgrading to ≥ 1.7.16 fixes both in the library.

**rpID and origin with separate app and API origins (P2, W1, R3).** Ceremonies run in the browser on `https://app.nunio.app`, and the API at `https://api.nunio.app` verifies them. `rpID` must be either `app.nunio.app` or `nunio.app`; the default `api.nunio.app` is invalid for the app origin. `origin` must be `https://app.nunio.app`. The same applies to staging (`app.staging.nunio.app`) and local e2e (`app.nunio.test:8443`, `origin` with the port). If production used `rpID: "nunio.app"`, browsers would also offer production passkeys on `app.staging.nunio.app`. Staging could not verify them, because its database differs and its `origin` is pinned, but the offer would confuse users. **Proposal:** in each environment, set `rpID` to the app hostname and `origin` to the app origin. The trade-off: moving the app to another hostname later strands existing passkeys, unless that hostname uses Related Origin Requests (W2) or the student signs in by OTP and adds a new passkey. ADR-0005 already rules out other hosts on the product domain.

**Registration (P2, P6, P7).** The client calls `authClient.passkey.addPasskey({name})`, which runs `GET /passkey/generate-register-options` and then `POST /passkey/verify-registration`. By default this needs a session that is fresh by `freshAge`. From 1.7.16 on it also checks the authoritative session store. Attestation is `"none"` and cannot be changed in 1.7.14. AAGUIDs are stored, but Apple reports zeros under `"none"`, per the plugin's own comment. `getAuthenticatorName(aaguid)` gives best-effort labels. `useAutoRegister` (conditional create) is passed through. SimpleWebAuthn documents it for use after a password-manager autofill (W3). **Unverified:** whether any browser auto-registers a passkey after an OTP sign-in.

**Passkey as the first credential (P2, P8).** Supported with `registration.requireSession: false`, `resolveUser` and/or `afterVerification` (which returns `userId`), and `createSession: true`. Better Auth does not create the user; nunio's callback does. For nunio, this would have to check the invitation and would still leave the email unproven. Pilot activation depends on email verification (R2), so an OTP would be needed anyway. Not recommended.

**Authentication and conditional UI (P3, P6, P8, W3).** The client calls `authClient.signIn.passkey({autoFill: true})` on mount, after `PublicKeyCredential.isConditionalMediationAvailable()`. The email input carries `autocomplete="username webauthn"`. Without a session the browser offers discoverable credentials, so `residentKey` should stay `"preferred"` or become `"required"`. Success creates a session through `internalAdapter.createSession`, so the repo's `session.create.before` checks (pending deletion, pilot activation) apply (C7, R1).

**Management (P4).** List, rename and delete exist. Delete and rename need only a session, not a fresh one. The table is described in P5. Known limitations: the user handle is random per registration (G5), and the requested name is used as the WebAuthn user name (G11).

## Removing passwords

- **Configuration (C1, C2, C4, E7).** Set `emailAndPassword: { enabled: false }`. That alone closes only `/sign-in/email` and `/sign-up/email`. **Proposal:** add these routes to `disabledPaths`:
  - `/verify-password`, `/change-password`, `/request-password-reset`, `/reset-password`
  - `/email-otp/request-password-reset`, `/email-otp/reset-password`, `/forget-password/email-otp`
  - `/send-verification-email`, `/verify-email` (link-based verification is no longer used)
  - `/email-otp/check-verification-otp`, unless the UI needs it

  `setPassword` is `createAuthEndpoint.serverOnly`, so it has no HTTP route (`api/routes/update-user.mjs:194`). Check the list against the router before finalising it. With `sendResetPassword` removed, `/request-password-reset` already fails with `RESET_PASSWORD_DISABLED`. Disabling it explicitly is defence in depth.
- **What stops working (C3, R1, R2).** The `/verify-password` check in `requestDeletion`. `revokeSessionsOnPasswordReset` and "password reset revokes all sessions" no longer apply. `afterEmailVerification` stays in the config but only runs on `/email-otp/verify-email` (E4); activation runs in `session.create.before` instead. `changeEmail` (core or OTP) is unaffected and stays deferred (R2).
- **Sensitive actions without a password (C3, C9, G4).** The current rule is password confirmation within ten minutes (R2). Better Auth offers only session age. **Proposal:** a sensitive action requires that the presenting session's `createdAt` is less than 600 s old. Otherwise the UI asks the student to confirm with a passkey or an email code. That is a normal sign-in: it sets a new session cookie, the request is retried, and the earlier session row stays valid until the student revokes it or it expires. For deletion this does not matter, since deletion revokes all sessions. Check this in nunio's own code, as `requestDeletion` does today. Do not set Better Auth's global `freshAge` to 600, because that would also make `/list-sessions`, `/unlink-account` and passkey registration require sign-in within ten minutes (C3, P2). Only the passkey registration change might be wanted.
- **Migrating existing users (C6, R5).** Users keep their `user` row and email address. Their next OTP sign-in creates a session for the existing verified user. Unverified (pending) users lose their `credential` row through C6 on their first OTP sign-in. Then they are verified, and the session hook activates their pilot if their invitation was accepted. **Proposal:** after the cut-over, delete `account` rows where `providerId = 'credential'` in a reviewed migration, so that no password remains usable through any route that is still mounted. No action is needed from students. The pilot cohort is small and invited, so a short notice email is optional.

## Fit with nunio's constraints (proposals unless marked)

- **Invitation-only registration.** Keep `user.create.before`; it fires on the OTP route with headers (C7). Add a `hooks.before` for `/email-otp/send-verification-otp` with `type: "sign-in"`. When no user exists for the address, it requires a valid, unexpired, unaccepted invitation for that exact address via `x-invitation-token`. Otherwise nunio would email codes to any address (E3). Keep `disableSignUp: false`, or the plugin would never create the invited account (E4).
  - **Gap 1:** the OTP route does not run the claim and the insert in one transaction (E4, C7). If the insert fails after the claim, which G6 shows can happen, the invitation is consumed and no account exists. One fix: let `user.create.before` also accept an invitation already accepted for the same address when no user exists.
  - **Gap 2:** the hook returns a distinct error for uninvited addresses, which reveals whether an account exists, on top of G7. This is acceptable for an invite-only pilot, but it is a choice (see Open questions).
- **Postgres-backed rate limiting.** The plugin rules automatically use the existing `storage: "database"` (C5). Add per-email limits in `hooks.before` for the send and sign-in routes, reusing the atomic upsert in `admitPasswordAttempt` (R1) under keys such as `otp-send:<email>` and `otp-guess:<email>`. Example: 5 sends per hour and 10 failed guesses per day per address. That caps guessing at roughly 10⁻⁵ per day per address. Alternatively raise `otpLength` to 8, which makes each guess 100 times less likely to succeed. Passkey routes have no plugin rule, so they fall under the global 100 requests per 10 s. Add a `customRules` entry for `/passkey/verify-authentication`.
- **Database sessions, cookie cache off.** No change. Every new path creates database sessions through the same hooks (C7). Passkey ≥ 1.7.16 also reads the session store authoritatively (P7).
- **Email verification and pilot activation.** OTP sign-in marks the address verified. Activation happens in `session.create.before`, which the repo already has. Rewrite the design doc's "retry" wording so this is the primary path.
- **Sensitive actions within ten minutes.** Covered above. Decide whether adding and deleting a passkey count as sensitive actions; the library requires neither a 10-minute session for adding nor any freshness for deleting (P2, P4).
- **Losing every passkey.** Signing in by OTP is always possible, so recovery needs no extra feature. The consequence: the student's mailbox becomes the root credential, as it already is with password reset by email. Passkeys improve speed and phishing resistance for students who use them, but they do not raise the floor while OTP remains a sign-in method.
- **Email content (R4).** Messages carry a code instead of a link. Keep the code out of the subject, because Scaleway keeps subjects while the domain is active. ADR-0013's sentence "Messages contain a verification/reset link" needs an update. Don't await the send if timing differences matter (E8). With the hook above, the difference is visible anyway.
- **Tests and UI (R6).**
  - The e2e fixtures that insert a `credential` account and sign in by password need another sign-in route. Options: read the code from the Scaleway stub, or use Chromium's virtual WebAuthn authenticator through CDP. **Unverified** for this setup.
  - The web app loses its password fields, the forgot and reset pages and their `proxy.ts` matcher entries, and the password field in the deletion dialog.
  - It gains a code entry step, a passkey button with autofill, and a passkey list in settings.
  - The client needs `emailOTPClient()` and `passkeyClient()`.
  - Prisma needs a `Passkey` model (P5) and a migration.

## Alternatives, as far as they bear on the decision

- **Magic link (C11):** single-use tokens with a 300 s expiry, in the same `verification` table. A link has to be opened in the browser that will hold the session, and the session cookie is set by `api.` (R3), so the link must go to the API, which then redirects to the app. A code works across devices. OTP is the simpler fit. Its re-authentication gap is the same (G4).
- **`lastLoginMethod` (C10):** tracks `email-otp` and `passkey` out of the box, in a cookie. It is useful only to steer returning students to "Use your passkey"; it is not needed for the decision.
- **`multiSession`:** lets one browser hold sessions for several accounts. It does not affect this decision. Not examined further.

## Confidence and gaps

High confidence in the 1.7.14 behaviour, which was read from the installed source, and in the passkey changes in 1.7.16, which were diffed and match the release notes. Not exercised: no flow was run against Postgres or a browser. Not verified:

- the exact list of password routes to disable (checked by grep, not against the built router);
- whether a `hooks.before` can return a silent `{success: true}` instead of throwing, to avoid revealing uninvited addresses;
- whether conditional create fires after OTP sign-in;
- the virtual authenticator approach for e2e.

Docs pages describe the latest release, not 1.7.14; differences were taken from source.

## Open questions

1. **Upgrade:** may `better-auth` (four packages) and `@better-auth/passkey` move together to ≥ 1.7.16, preferably the latest 1.7.27, as part of this change? Or should nunio stay on 1.7.14 with the `afterVerification` workarounds?
2. **RP ID:** the app hostname per environment (narrow; a later move strands passkeys), or `nunio.app` (broader; staging and production share passkeys in the browser's picker)?
3. **Passkeys:** required, prompted after first sign-in, or optional in settings? With OTP always available as a fallback, should a student be able to switch off email-code sign-in once they have a passkey? Better Auth has no built-in support for that.
4. **User verification:** require biometric/PIN for every passkey (`"required"`), which excludes some security keys without a PIN, or accept presence-only?
5. **Sensitive actions:** does "signed in within the last ten minutes" replace "password confirmation within ten minutes" in the design doc? Do adding and deleting a passkey count as sensitive actions?
6. **"Remember me":** OTP and passkey sessions always last the configured 30 days. Drop the "remember me" option, or shorten `expiresIn`?
7. **Revealing accounts:** is it acceptable that the send step tells uninvited addresses apart from existing accounts? Or should uninvited sends answer `{success: true}` without sending, at the cost of a silent failure for a mistyped address?
8. **Code format:** 6 digits with a per-email limit, or 8 digits? `storeOTP` `"encrypted"`, `"hashed"`, or plain?
9. **Cut-over:** delete `credential` rows immediately, or after a grace period? Send pilot students a notice?
10. **Records:** does this change warrant a new ADR (passwordless authentication; supersedes parts of the identity design doc and of ADR-0013's email-content sentence)?
