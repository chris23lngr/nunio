## Proposed nunio integration boundaries

These are engineering proposals inferred from the brief and evidence above; API names in this section belong to future application design unless explicitly listed in the source map.

### Identity

- Keep the Better Auth server instance in a server-only package consumed by the API. The browser receives the client; workers act under a stored responsibility grant, not a captured browser session token.
- Prefer one public origin with `/api/*` routed to the independently deployed API. Separate deployables do not require cross-origin browser cookies. If separate origins are necessary, test credentialed CORS, exact origin allowlists, cookies, callback URLs, and proxy headers end to end.
- Start with database-backed sessions and cookie caching disabled. Recheck authoritative session state for new grants, deletion, integration changes, and submission approvals. Preserve every `Set-Cookie` response header; do not blindly copy a generic header loop if it merges multiple cookies.
- Use a Fetch-compatible dedicated API on Bun; mount the original request through `auth.handler(request)` without consuming its body first. tRPC or REST is a separate transport decision; Better Auth does not need to be wrapped in a tRPC procedure. Fastify is an optional alternative, not a commitment. If used, its [documented integration](https://better-auth.com/docs/integrations/fastify) provides `fromNodeHeaders(request.headers)` for Node-style headers. Production URL construction must use the configured canonical origin/trusted proxy contract. Auth mounting and Stripe raw-body parsing need separate route handling.
- Proposed compatibility baseline: pin Prisma 7 CLI/client/driver adapter and Better Auth versions proven together. Read the versioned v7 docs, generate the auth schema, review the resulting Prisma migration, explicitly generate the client, and execute signup/session/revocation plus application transactions under Bun. Run the same checks against the deployed API runtime. A Bun package manager does not prove every hosting target executes Bun.
- Maintain domain authorization in shared application rules: authenticated actor, resource owner, selected context, action grant, current revocation state, and permitted destination. Test cross-user access in API routes, queued jobs, retrieval, exports, and file downloads.
- Sessions, responsibility grants, and paid entitlements are three different state machines. Signing out need not cancel previously authorized background work; pausing/revoking a responsibility must stop subsequent actions even if its queue item predates revocation.

### Billing and capped usage

- The free pilot receives explicit entitlements with no fixed expiry and a finite Allowance in nunio, independent of Stripe subscriptions (founder decision, 2026-10-30). Access ends through explicit founder revocation; additional Allowance is granted manually, without an automatic reset. Enforce atomic usage reservations before costly work and reconcile actual cost afterward. Subscription status alone does not prevent concurrent jobs overspending an allowance.
- Add Stripe hosted Checkout and Portal when paid plans are ready. Permit only server-approved plan/price IDs and return URLs. Do not let a user submit another customer's ID or grant access from a browser success redirect.
- Proposed webhook ingress: read bounded raw body → verify signature → atomically insert a unique event inbox record plus durable work intent → return success. The worker applies an idempotent transition and marks processing complete. If durable persistence fails, return failure so Stripe can retry.
- A crash after receipt must not permanently mark unfinished processing as complete. Replays and manual redelivery must remain safe. Use unique business-operation IDs as well as event IDs for side effects, without collapsing all future updates to the same subscription into one event.
- Define explicit states for pilot, active subscription, payment trouble, cancellation at period end, expired access, and budget exhaustion. Reconcile authoritative subscription state to tolerate reordered events. Maintain read access/export/reminders according to the product policy when AI execution is paused.
- Pin the Stripe SDK and event API version, test snapshot event parsing against that pair, and avoid copying preview event-destination registration examples. Do not log secrets or raw billing payloads unnecessarily.

### Files and agent execution

- Quarantine uploads before parsing/indexing; apply byte/page/decompression/time limits. Process document formats in an isolated environment without unnecessary network or credentials. Scanning is one layer, not proof that a document is safe.
- Authorize both ingestion and retrieval. Selected course/material context must be enforced in database/search queries and downloads, not merely described in prompts. Preview generated HTML/Markdown with safe rendering rules.
- Tool execution revalidates grant version, owner, scope, destination, current budget, and approval bound to the artifact/version and arguments. An approved artifact changed after review requires fresh approval unless an explicitly applicable automation grant permits it.
- A model asking for a tool does not establish consent. Treat returned tool text as untrusted too. Store security-relevant action metadata and outcomes with redaction; exclude credentials and unnecessary course content.

## Verification cases to carry into the plan

1. User A cannot read or mutate user B's course, file, retrieval result, queued action, billing portal, or export by changing an ID.
2. Expired/revoked sessions cannot approve actions; a paused grant prevents a previously queued job from executing its next external action.
3. Untrusted origins cannot perform authenticated mutations; production proxy/header spoofing cannot alter callback destinations or evade trust rules.
4. Malformed, oversized, malicious, or mislabeled uploads do not reach retrieval or escape parser isolation.
5. A syllabus containing instructions to exfiltrate files cannot expand context or invoke an unauthorized destination.
6. A signed Stripe event delivered twice, out of order, or after a worker crash converges on the correct entitlement state without duplicate side effects. Modified raw bodies and incorrect secrets are rejected.
7. Visiting a checkout success URL without a verified entitlement does not enable paid AI work. Concurrent reservations cannot exceed the hard allowance.
8. Revoke/disconnect/delete behavior remains effective after restarts and restores; reconciliation does not resurrect deleted grants or content.

## Confidence and gaps

High confidence in the documented interfaces and security boundaries; no runtime compatibility has been proven. The repository has a product brief but no application packages to inspect. Prisma 8's release-candidate docs now occupy unversioned URLs while Better Auth documents Prisma 7; use a deliberate version boundary. Better Auth's Prisma import variants are confirmed by its source re-export, but the installed package exports must still be checked. Stripe event APIs have also evolved, so copy patterns only after checking pinned versions.

Still required: select supported sign-in methods, email delivery, credential recovery/MFA policy, exact deployment origin/proxy layout, database transaction implementation, session/grant retention, payment grace policy, usage units, and provider-specific token encryption/revocation. These choices do not follow automatically from installing Better Auth or Stripe. EU processing, provider contracts, and legal obligations require separate evidence; this note makes no compliance claim.
