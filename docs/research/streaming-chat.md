# Streaming grounded Chat responses

Research date: 2026-11-10. Scope: research only in `feat-ui-textarea`; no implementation, installation, live model calls, commits, or deployment. Inputs: [web conventions](../../apps/web/README.md), [knowledge design](../design/knowledge-retrieval.md), [ADR-0005](../adr/0005-separate-app-and-api-origins.md), [ADR-0012 including amendments](../adr/0012-openrouter-eu-as-interim-ai-provider.md). **Repository observations** below describe the inspected checkout. **Recommendations** are proposed changes, not existing behavior. Official documentation and installed package source were checked; compatibility is not a completed runtime test.

## Implementation status

Implemented on this branch: the Answerer uses `streamText` when a text callback is supplied; Knowledge consumes generation inside the existing meter and persists only complete results. `POST /api/me/chats/{id}/messages/stream` emits AI SDK UI-message SSE, with separate committed/refused outcomes. The JSON endpoint remains available. Reasoning is forwarded as transient `data-reasoning` events (text deltas and streaming state) and shown only during the active send; it is cleared on completion, failure, Stop, or navigation and is never added to persisted history. Chat uses `DefaultChatTransport`, keeps persisted history in React Query, batches provisional Markdown updates every 50ms, and supports Stop, draft recovery, and cancellation on navigation/unmount.

Verified with provider SSE fixtures (including missing usage, truncation, errors and incomplete streams), HTTP/Postgres tests (including Source deletion and held usage after abort), screen tests, and an actual HTTPS streaming browser fixture. Live provider cancellation and deployed proxy buffering/duration still need the staging smoke check described below. Stop cancels answer generation; retrieval embeddings already in progress retain their own existing metering/deadline.

## Finding and recommendation

Use the Vercel AI SDK already installed, retain OpenRouter and the existing API deployment, and stream **provisional text** through the existing knowledge/meter/persistence flow. The smallest fit for current web rules is a React Query send mutation using `DefaultChatTransport` from `ai` directly, with a small reducer for text and domain-result chunks. Keep Query as owner of persisted history and keep a single ephemeral draft outside its cache. `useChat` is compatible, but making it the message owner would require an explicit exception to the current web convention and careful removal of competing state.

Do not return the provider stream directly from the API: a provider's successful finish is earlier than allowance settlement, source revalidation, encrypted persistence, and citation resolution. Emit a distinct domain **committed result** containing the canonical question and answer only after these succeed. EOF or a model `finish` is not proof that messages were saved.

Assumptions for the smallest first iteration: one active send per screen, no automatic generation retries, no resume infrastructure, no tools in the browser; reasoning is transient during the active send, no new conversational context behavior, and only complete successful answers persisted. Cancellation leaves a visible local incomplete state until dismissed or refreshed. Persisting failed questions or partial answers is a separate product/schema decision.

## Repository observations and constraints

- [AI dependencies](../../packages/ai/package.json) pin `ai@7.0.157`, `@openrouter/ai-sdk-provider@3.1.0`, and Zod 4.6.7. [Answerer](../../packages/ai/src/answer.ts) calls `generateText`, requires `finishReason === "stop"`, strips unrecognized `[S<number>]` tags, then derives cited tags. The prompt contains retrieved data and the current question; **it does not send earlier messages**. Streaming must not silently change that scope.
- [Model registry](../../packages/ai/src/models.ts) owns model choice, output limits (8,000 for explanation), conservative reservation estimates, `maxRetries: 0`, ZDR/data-collection restrictions, and actual micro-USD calculation. OpenRouter reported cost wins; absent cost falls back to token counts. Missing counts currently become zero; **recommendation:** never classify an interrupted stream with missing usage as a zero-cost success.
- [Chats](../../packages/knowledge/src/chats.ts) owns retrieval from the authenticated Chat selection, metered generation, canonical message IDs, and a transaction recording the question and assistant together. It rechecks Chat existence and all source keys after generation. It encrypts assistant content under every retrieved Source dependency, not just cited Sources. On later reads any missing dependency yields `text: null`; citations resolve at display time and can become `gone`. Source-free answers and student questions currently have no source-dependent encryption. Preserve these existing distinctions.
- [Meter](../../packages/delegation/src/meter.ts) atomically reserves allowance before calling the model, checks entitlement/deletion/kill switch, supplies a 120-second timeout signal, and settles only after the callback resolves with usage. Definite rejection releases the reservation; abort/network/uncertain failure holds it for reconciliation. The current meter options accept a timeout, **not an external cancellation signal**. Retrieval embeddings have their own metering path.
- [API routes](../../apps/api/src/chats.ts) expose strict `{ text }` POST JSON, trimmed 1–4,000 characters, and authenticated history GETs. [Application middleware](../../apps/api/src/create-app.ts) permits exactly `appOrigin` with credentials and rejects mutating `/api/me/*` requests from other/missing Origins. [Vercel config](../../apps/api/vercel.json) uses framework `hono`, compiled `dist`, Node 24, and `fra1`; [entrypoint](../../apps/api/src/index.ts) exports a Hono application. No chat-specific duration is configured.
- [Web conventions](../../apps/web/README.md) assign server state to React Query, transport/session adaptation to infrastructure, streaming orchestration to the feature/screen, and display to props-only components. Mutations have no automatic retry; session transitions clear caches. [Web API adapter](../../apps/web/lib/api-client.ts) converts 401 to `ApiError`; a new SDK fetch path must preserve this boundary rather than bypass session-expiry handling.
- The current [send mutation](../../apps/web/features/chat/api/chat-mutations.ts) consumes final JSON; [screen](../../apps/web/features/chat/chat-screen.tsx) inserts canonical question/answer IDs after success and revalidates on failure. [MdxContent](../../packages/ui/src/components/ui/mdx/mdx.tsx) is actually `react-markdown` with GFM/math/KaTeX and `skipHtml`, not an MDX compiler. Its [reference plugin](../../packages/ui/src/components/ui/mdx/references.ts) links only supplied tags. The ongoing UI work may change screen markup; this proposal does not require replacing it.
- The latest ADR-0012 amendments explicitly use **international**, ZDR routing; the earlier EU-only decision is superseded for now. `fra1` hosting alone does not establish EU inference. Keep the existing provider settings and disclose the actual model data-handling label.

**Version proposal:** retain `ai@7.0.157` and provider `3.1.0`; add `ai@7.0.157` as a direct dependency only where imported (API and web for the proposed protocol adapter). No React hook package is required. If choosing `useChat`, pin `@ai-sdk/react@4.0.161`: registry metadata declares exact `ai@7.0.157` and React peer `^19.2.1` covers the repo's React 19.3.1. Registry latest on the research date was React adapter 4.0.170 with exact AI 7.0.166; installing latest casually creates version drift. **SDK 7:** use standalone `toUIMessageStream({ stream: result.stream })` and `createUIMessageStreamResponse`, rather than deprecated result instance response methods. `onEnd` replaces `onFinish`; old aliases still exist. Avoid copying v4/v5 numeric data-stream framing or assuming old hook arguments. [v7 migration](https://ai-sdk.dev/docs/migration-guides/migration-guide-7-0), [installed SDK declarations](../../packages/ai/node_modules/ai/dist/index.d.ts).

**Wire:** the UI-message protocol is SSE, with `x-vercel-ai-ui-message-stream: v1`, `start`, text block start/delta/end IDs, domain data parts, errors, and finish framing. Plain text streams omit the domain envelope needed here. Use SDK helpers/parser rather than splitting network chunks into JSON lines. [Protocol](https://ai-sdk.dev/docs/ai-sdk-ui/stream-protocol). `createUIMessageStream`/response helpers can mix model output with application data and transient notifications. [Custom data](https://ai-sdk.dev/docs/ai-sdk-ui/streaming-data).

**Cookie transport:** `DefaultChatTransport` accepts an absolute API URL, `credentials: "include"`, a fetch override, and request preparation. Its public `sendMessages` returns a stream of parsed `UIMessageChunk`s independently of React hooks. Override request preparation to send only `{ text }`, with Chat identity in the route, rather than trusting client-supplied history/model/citations. [Transport docs](https://ai-sdk.dev/docs/ai-sdk-ui/transport), [installed transport](../../packages/ai/node_modules/ai/src/ui/http-chat-transport.ts), [installed parser](../../packages/ai/node_modules/ai/src/ui/default-chat-transport.ts).

**Hono/Vercel:** Hono can return streaming Web Responses, and Vercel explicitly documents Hono streaming. Keep generation in `apps/api`; a Next.js proxy is unnecessary. Once streaming has started, Hono's normal error handler cannot replace the response: errors must be encoded and cleaned up inside the stream operation. [Hono helper](https://hono.dev/docs/helpers/streaming), [Vercel Hono](https://vercel.com/docs/frameworks/backend/hono). Preserve credentialed CORS on error and streaming responses and preflight handling. `exposeHeaders` is available if client code must read a custom response header; the protocol header need not be read by a decoder that already knows the protocol. [Hono CORS](https://hono.dev/docs/middleware/builtin/cors).

## Proposed end-to-end lifecycle

1. Keep create/history JSON APIs. Add a narrowly documented streaming POST, e.g. `/api/me/chats/{id}/messages/stream`, with the same validation/auth/origin rules. This avoids breaking existing generated JSON clients during migration. Describe `text/event-stream` plus prestream JSON errors in OpenAPI and regenerate the schema when implementing; don't make openapi-fetch's JSON decoder parse SSE.
2. Extend the Answerer public seam with streaming deltas plus a terminal result. Knowledge remains responsible for selection, billing, canonical text/citations, and storage. Inside `delegation.meter`, **consume the stream to completion**, forwarding deltas through a narrow callback. Returning a stream handle from the metered callback would settle before actual generation and is incorrect.
3. Use one SDK stream consumer to accumulate answer text and terminal usage/metadata. Observe error events as well as thrown failures; a stream that emits an error and then closes must not become success. Keep registry call settings and retries disabled; do not opt into `streamRetries`/callback retries. SDK stream errors and callback semantics are documented in the [streamText reference](https://ai-sdk.dev/docs/reference/ai-sdk-core/stream-text).
4. Forward text deltas and transient reasoning deltas to the API's UI-message writer. An optional trusted citation map can be sent after retrieval; otherwise show plain provisional tags until commit. Reasoning can itself quote course material and has the same provisional-disclosure limits as answer text. Never forward prompts, retrieved excerpts as separate data, tools, raw errors, or arbitrary provider metadata. The API owns framing; do not forward the provider's `finish` as application success.
5. After a normal stop with trustworthy usage, finish metering; sanitize complete citations; run the existing encryption/persistence transaction; resolve provenance again. Then emit a typed `data-committed` carrying the existing JSON question/answer shape, followed by the UI finish. A source deleted during generation causes a withdrawn/unavailable outcome instead of commit. No pending answer belongs in a plaintext DB/log/resume cache.
6. The web send mutation consumes SDK chunks into **one provisional draft**, then accepts only `data-committed` as success and updates Query with canonical IDs/text. If the stream ends without that result, treat it as interrupted and revalidate history: persistence might have succeeded just before the connection broke. Keep the requested instant composer clearing: retain the submitted text in the ephemeral send state for recovery, restore it on failure, and do not automatically resend. Clear drafts on account/session/Chat changes and dispose the old request so late deltas cannot enter another Chat.

**Prestream errors:** reject invalid input/auth/ownership before creating the streaming response. Retrieval/allowance checks may occur during stream execution; for the smallest callback-based implementation those refusals become typed stream outcomes. If preserving HTTP 403 for every usage refusal is required, introduce a prepare/reserve phase before headers; that is additional interface work. Do not promise HTTP status changes after the first byte.

## Cancellation, failures, persistence, and usage

Forward request/Stop cancellation and meter timeout together using `AbortSignal.any`; check already-aborted requests before starting a provider call. Prefer exposing an optional signal at the meter boundary so its generated deadline combines consistently; cancellation must cover retrieval too if Stop promises to stop all work. AI SDK supports provider `abortSignal`, `onAbort`, and hook `stop()`. Abort and resumable streams are incompatible in the documented hook design. [Stopping streams](https://ai-sdk.dev/docs/advanced/stopping-streams).

OpenRouter notes that cancellation depends on upstream support and unsupported providers can continue processing/billing. Never promise immediate billing stop. Midstream provider errors can arrive in ordinary SSE data even after HTTP 200. [OpenRouter streaming](https://openrouter.ai/docs/api_reference/streaming). Confirm disconnect propagation in the actual Hono/Vercel Node deployment; an in-process Request signal test proves only the local seam.

Preserve current conservative accounting initially: aborted/error/unknown calls throw and leave reservations held; definite 4xx rejection releases; successful terminal usage settles. A truncated (`length`), filtered, or otherwise incomplete answer is not a canonical completed answer. If trustworthy billed usage accompanies an unsuccessful finish, a useful follow-up is returning a metered **outcome** with usage so billing settles while Chat still refuses persistence. Do not fake success just to settle, or release because no text reached the browser. If usage is absent after disconnect, retain the hold and reconcile through existing operations.

OpenRouter's current accounting docs say usage is returned automatically and mark Chat Completions `usage.include`/`stream_options.include_usage` deprecated; the repo still sends `usage.include`. Preserve it during streaming work unless a focused compatibility test justifies cleanup. The docs now emphasize Responses API terminal events; the repo uses `.chat()`, so test **Chat Completions fixtures**, including final usage-only chunks and `providerMetadata.openrouter.usage.cost`. [Usage accounting](https://openrouter.ai/docs/guides/guides/usage-accounting).

The SDK persistence guide explicitly omits authorization/production handling. Its generic storage and disconnect-completion pattern must not replace nunio's source-key wrapping or imply durable background execution. [Persistence guide](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-message-persistence). Keep work attached to response consumption; set a bounded application timeout below the actual function duration, leaving time for settlement/storage. Verify the generated Hono function config and staging behavior; copying a Next.js route `maxDuration` export into a helper file does not establish that limit. [Vercel duration configuration](https://vercel.com/docs/functions/configuring-functions/duration).

## Incremental rendering and deletion implications

Recommendation: first use the existing `MdxContent` for accumulated provisional Markdown, updating at a modest cadence rather than recompiling on every token. Final rendering must use canonical sanitized text and canonical citations. Unfinished fences, tables, math, links and `[S` prefixes are normal streaming inputs: verify they remain readable and never throw. Keep `skipHtml` and supplied reference mapping; do not evaluate generated JSX. A stream-aware Markdown library is optional only if measurements show unacceptable flicker/cost; it is not required to unlock streaming.

Provisional text may contain an invalid tag until final sanitation. It must never become a trusted clickable citation. If the requirement is that invalid tags never appear at all, use an incremental tag sanitizer with carry across chunk boundaries; a regex independently applied to deltas is incorrect. Server-provided citation mappings must never be constructed from model URLs.

Streaming discloses answer bytes before the final source-key check. Deleting a Source can suppress persistence and replace the live draft on detection, but cannot recall bytes already delivered. This is a product/privacy choice, not solved by encryption at rest. Keep no persistent browser draft storage, withdraw on detected deletion, and ensure source deletion refreshes affected Chat history. Define cross-tab deletion behavior if immediate withdrawal everywhere is required. The existing source-key checks establish canonical-history deletion, not revocation of already read information.

## Open product decisions

- May provisional text be shown before the final deletion check? Recommendation: yes with explicit provisional status and withdrawal, acknowledging already delivered bytes cannot be revoked.
- Should Stop abort generation, or only stop following a response that still saves? Recommendation: abort, no resume, held uncertain billing initially.
- Should failed/stopped questions and partial answers survive refresh? Recommendation: no schema change initially; keep the draft locally, and clearly label it unsaved. Durable partials require source-dependent encryption, completion status and retry/idempotency design.
- Is this still independent grounded questions, or a contextual conversation? Recommendation: preserve independent questions; adding history changes cost estimates, source scope and deletion dependencies.
- Is adopting `useChat` itself a requirement? Recommendation: use its underlying SDK transport within Query first. If adopting the hook, make it the sole live-message owner and document the convention exception rather than synchronizing two message stores.
- Do users need safe retry after a lost commit acknowledgment or simultaneous multi-tab sends? Current endpoints have no per-turn idempotency key; refetch before manual retry reduces ambiguity but does not give exactly-once turns. Add server-owned request deduplication only if that guarantee is required.

Follow-up UI context: the composer now clears immediately on submission and restores failed drafts; the streaming implementation must preserve that behavior.

Confidence: high on the inspected public seams and documented API compatibility; medium on provider terminal usage/cancellation until fixtures and a staging stream prove them.
